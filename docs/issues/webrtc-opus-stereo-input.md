# WebRTC Opus stereo input

Status: resolved on 2026-09-20; hosted speech-quality acceptance remains open

## Summary

Vxpipe accepts mono and stereo audio in the standard 48 kHz WebRTC Opus RTP mapping. The RTP
mapping remains the two-channel decode envelope used by readiness and room media. The Gateway
keeps one decoder history for each input stream, normalizes mono and stereo packets to the
selected provider's strict mono format, and keeps the original provider descriptor unchanged.

The packet mode cannot be inferred from the SDP RTP channel count or the Opus `stereo` format
parameter:

- `opus/48000/2` is the normal RTP mapping and does not prove every packet contains stereo.
- The SDP `stereo` parameter describes a decoder preference. It does not describe the next
  packet sent by the peer.
- The `s` bit in the first byte of an Opus packet's TOC identifies whether that packet contains
  mono or stereo audio.

These rules come from [RFC 7587 section 6.1](https://www.rfc-editor.org/rfc/rfc7587.html#section-6.1)
and [RFC 6716 section 3.1](https://www.rfc-editor.org/rfc/rfc6716.html#section-3.1).

## Implemented boundary

The implementation uses the same precompiled libopus distribution already supplied by
`membrane_opus_plugin`. A small Gateway Unifex adapter exposes libopus's fixed mono-output decoder
without the plugin wrapper's packet-channel equality check. The adapter adds no codec library,
Rust NIF, shared codec process, fallback provider or replay path.

1. Readiness advertises the negotiated Opus decode envelope, normally two channels.
2. `SpeechInput` owns one mono-output libopus decoder resource inside the connection process.
   Every packet in that input stream advances the same decoder state.
3. Libopus decodes both mono and stereo packets directly into mono PCM. Negotiated channel
   metadata never bypasses packet validation or state advancement.
4. A mono-PCM provider receives decoded mono PCM directly. A mono-Opus provider owns one
   stateful mono encoder and every packet is encoded through it with the original RTP timestamp
   projection.
5. The input decoder and optional provider encoder each retain one continuous history for the
   lifetime of that prepared speech input.
6. Empty and invalid packets are dropped without terminating the connection. Receive-only
   connections discard input before packet inspection.

Room audio uses the same stateful decoder through a connection-owned Membrane element. That
element replaces the old decoder-plus-mixer pair and emits mono PCM for the room clock. Speech
normalization stays connection-local and feeds only that participant's media ingress; it does
not introduce cross-call ownership.

An intermediate candidate decoded every packet but forwarded raw mono Opus while re-encoding
stereo packets. A continuous downstream decoder proved that this spliced two incompatible
encoder histories: the first forwarded mono packet after stereo differed from its correct
decode by RMS 4,567.8 with a maximum sample error of 14,174. Another shortcut trusted matching
negotiated mono metadata and forwarded a real stereo packet unchanged. Both shortcuts are
removed; passthrough is available only for formats with fixed packet semantics.

## Verification

Focused tests use real packets generated by `Membrane.Opus.Encoder.Native` and cover mono,
stereo, mono/stereo transitions, one continuous decoder history, exact mono PCM output, mono
Opus output history, matching negotiated metadata, invalid input, empty RTP and receive-only
input. A red room-pipeline regression
first proved that changing decoder resources at packet-mode boundaries changed PCM output. The
speech and room paths now exactly match independent single-history decoder resources. The
Opus-output regression matches an independent continuous encoder packet for packet. The
deterministic callback regression proves both packet classes return `:noreply` where the rejected
candidate returned `:stop`.

A supervised capability plus a real media ingress caught a separate integration-boundary
regression: the capability's input binding exposed codec and sample rate but omitted channels,
so `SpeechInput` rejected every provider before normalization. The red test failed with
`{:error, :unsupported_audio}`. The binding now carries codec, sample rate and channels, and the
same test prepares successfully. The full local PeerConnection path also reaches `bot-ready`
and delivers normalized stereo and following-mono packets.

The committed benchmark runs with `+S 4:4` on the eight-scheduler, 16 GiB development host. Its
final paced lanes processed 3,200 packets each for 32 synchronized calls at 50 packets/s per
call. Two consecutive controlled runs of full decode-and-encode transitions completed at 5.135
and 5.514 ms p99 with operation p99 of 0.868 and 1.125 ms. Both missed zero 20 ms deadlines.
Average scheduler use was 12.74% and 15.00%, with maxima of 15.78% and 16.55% across the four
enabled schedulers. Their no-codec transition controls completed at 2.193 and 2.206 ms p99.

The unpaced transition lane sustained 9,861.9 and 9,880.1 packets/s in those runs, with operation
p99 of 1.111 and 1.067 ms. The first post-repair paced transition run recorded five deadlines
above 20 ms; all excess was in scheduler wakeup lag, while codec operation stayed below 2.7 ms.
The two immediate identical runs recorded zero misses in every control and normalization lane.
The anomaly was not accepted as a change-caused codec failure. These results establish local
codec headroom, not production call capacity or hosted recognition quality.

All five umbrella gates pass after the final repair. The bounded root test completed 1,937 tests
with zero failures and 41 exclusions using seed 530504.

## Remaining limits

- Mono Opus re-encoding accepts libopus frame durations from 2.5 through 60 ms. A larger
  aggregate packet is dropped because the provider input contract carries one raw Opus packet;
  supporting multi-frame re-packetization needs a separate design.
- Local codec success does not establish Deepgram or another hosted provider's recognition
  parity. Run the tagged live lane when credentials and fixture audio are available.
- The full local PeerConnection test covers empty, stereo and following-mono RTP and currently
  passes. Hosted recognition quality still requires the tagged live lane.
