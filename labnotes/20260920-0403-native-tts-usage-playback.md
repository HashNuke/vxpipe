## Decision

When a native TTS session starts with `usage: true`, Channel attaches a
payload-free cumulative `Speech.TTSUsage` snapshot to the existing bounded
`Speech.Event` and `Speech.Audio` envelopes. There is no separate usage
message, process, registry, table, receipt or journal.

A snapshot contains the allocation and request references, validated usage
identity, optional bounded provider request ID, immutable submission provenance,
input character count, cumulative generated bytes and generation state. It
contains no input text, PCM, credential, URL, header or raw provider response.
Inspection omits provider identity and provider request IDs.

`usage: false` is the default until room migration in checkpoint E connects
these snapshots and authenticated playback returns to the existing
`Usage.TextToSpeechAttempt` accumulator. Admission alone and definite
pre-submission rejection produce no snapshot.

## Ordering and bounds

Channel creates the submission snapshot after it accepts a provider
`input_submitted` event and before it replies to that provider. It increments
the generated-byte total, attaches the resulting snapshot to the PCM envelope,
and dispatches that envelope before returning its exact credit reference.
Terminal snapshots are attached after terminal metadata is validated and before
the terminal event is queued. If a zero-audio request completes or cancels before
the consumer acknowledges `input_submitted`, Channel sends the matching terminal
event in provider order before accepting it, then promotes that already-delivered
event after the submission ACK without sending a duplicate.

Channel sends the submission event before its first audio envelope. It may place
both in the consumer mailbox before the submission event is acknowledged, which
closes the provider-success/failure gap without blocking the provider callback.
Audio validation and sink credit remain unavailable until the matching submission
event is acknowledged. A new request is rejected while an earlier event is still
awaiting acknowledgement, so a submission cannot queue behind unrelated control.

The same acknowledgement protocol that bounds semantic events and PCM envelopes
therefore bounds their usage evidence:

- one semantic event occupies the current acknowledgement slot; only its matching
  terminal may additionally be pre-delivered while submission holds that slot;
- one PCM chunk can await sink credit;
- advancing either stream cannot leave a second per-chunk usage stream queued;
- a fence may revoke live media authority but cannot alter the immutable usage
  snapshot already delivered in that envelope.

Consumers must acknowledge an event before acting on its live semantic fields.
The attached Channel-created usage snapshot is historical delivery evidence and
may be retained if later allocation loss makes that live acknowledgement fail.

A provider request ID may first appear at submission or at the terminal event.
Channel keeps the first bounded value, accepts the same value again and rejects a
conflicting value.

## Playback and settlement

Generated completion and actual playback stay separate:

1. `generation: :completed` means no more PCM will be generated after final
   credit.
2. `Session.cancel/3` accepts an authenticated, monotonic sink playback report
   and returns bounded request and cumulative session playback totals. Channel
   never infers audibility from generated or credited bytes.
3. A successful cancellation return proves the provider callback accepted the
   cancellation and returns the recorded playback. If the terminal arrived first,
   that return also settles the request. If the callback returns first, replacement
   remains blocked until the terminal event arrives and Channel settles it.
4. Channel clears the request and permits replacement only after callback and
   terminal-isolation barriers have both passed.
5. Cancellation during completed sink drain updates playback without publishing
   a second generation terminal.

The authorized consumer already owns its usage accumulator and the returned
playback value. Duplicating playback or settlement in another asynchronous fact
would create another flow-control path and another state representation.

## Failure semantics

The failure tests capture and monitor the exact live Channel, then hold the actual
consumer before submission. The provider observer confirms both its submission
event and first PCM call returned successfully while the submission ACK is still
withheld. The test kills the provider allocation, whole capability scope or
independent lifetime owner, observes that exact Channel's `:DOWN`, and only then
releases the consumer. Its ordered mailbox still contains both the submission
event and first audio envelope with the submitted provider identity and cumulative
generated-byte snapshots. This proves historical delivery through the tested
failure boundary without using a permissive dead-PID check.

Live event or audio acknowledgement after allocation loss still rejects. The
historical snapshot is a copy validated and attached by Channel before it
accepted the corresponding provider operation; allocation revocation does not
erase that copy.

Two zero-audio failure tests hold the submission ACK while the provider reports
its request ID only at `completed` or `cancelled`. They then revoke the allocation
after the provider has received `:ok`. Both ordered envelopes, including the
terminal-only provider ID, remain in the consumer mailbox after the exact Channel
goes down. This closes the same accepted-but-buffered failure window for terminal
metadata without adding another message type or state owner.

## Rejected alternatives

- A speech-owned ledger or ScopeControl field fails with the whole speech scope.
- Standalone usage messages can accumulate while a consumer selectively receives
  and acknowledges media. Sharing the same PID does not prevent that selective
  receive backlog.
- A separate usage PID creates another flow-control relationship.
- Packed atomics, ETS and a custom journal add a second storage protocol.
- Deriving playback from generated or credited PCM would claim audibility the
  provider and Channel cannot observe.

## Verification evidence

The first standalone-message candidate appeared bounded when its collector
coalesced by request, but Astra review found that the collector measured its map
rather than its mailbox. A focused red test reproduced the issue: a
16-character Morse request accumulated **77 standalone usage messages** while
the consumer kept acknowledging event and audio envelopes. The repaired test
drains the same request with **75 audio envelopes**, verifies a monotonic snapshot
inside each envelope and a terminal total of **24,000 generated bytes**, and
observes no independent usage message.

The focused TTS selection passes **38 tests**. The broader speech, Morse and usage
selection passes **164 tests** with seed 530504. It includes:

- zero usage for admission-only and definite pre-submission rejection;
- exact-Channel-DOWN survival across provider/allocation, whole-scope and
  independent lifetime-owner loss;
- zero-audio completion and cancellation retained behind a held submission ACK,
  including a provider request ID first reported at the terminal;
- live promotion of a pre-delivered terminal after submission ACK, including
  early-ACK rejection, no duplicate delivery, settlement and replacement;
- final-credit completion gating and a provider ID first reported at terminal;
- monotonic generated bytes inside bounded envelopes;
- authenticated request and cumulative session playback;
- completed sink drain followed by a clean replacement;
- long-phrase drain, output limits and redaction.

The updated cancellation load passes all **18 trials** across 1, 8 and 32
concurrent scopes: **5,904** cancellation/replacement/STT cycles and **132,840**
usage-bearing envelopes. Every cycle rejects stale credit and timer work,
preserves exact replacement PCM and STT text, checks there is no standalone
usage-message stream, and returns to **244** processes. The raw artifact is
[20260920-0921-tts-cancellation-usage.json](20260920-0921-tts-cancellation-usage.json).

Against D2's same-workload run, the median trial p95 first-audio duration changes
from 216.5 to 205 microseconds; cancellation return changes from 145.5 to 112
microseconds; replacement first audio changes from 166 to 164 microseconds; and
STT end changes from 273.5 to 239.5 microseconds. The maximum trial p95 first-audio
duration changes from 1,042 to 1,026 microseconds. Individual trials vary in both
directions. This establishes no earlier correctness, concurrency or cleanup
failure in this bounded run; it is not a production latency guarantee.

The workload uses local Morse PCM, caller-supplied playback reports and no room,
physical sink clock, hosted provider, codec conversion or network. Checkpoint E
must connect the bounded evidence to room attribution and repeat sink/playback
checks through real room composition.

Formatting, warnings-as-errors compilation, strict Credo and unused-dependency
checks pass. Two default-concurrency umbrella attempts and one four-case-capped
attempt were not accepted: failures moved across unrelated MCP, room, recording,
tool, Morse, WebRTC and Telnyx deadlines as machine pressure increased. The first
run's two exact failures passed alone. Inspection found load average above the
8-CPU machine's capacity, substantial unrelated CPU use, heavy memory compression
and a 98%-used data volume. No further broad run was made in this checkpoint; this
environment limitation remains an acceptance gate rather than a D4 stability claim.
