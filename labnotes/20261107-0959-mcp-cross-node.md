# MCP cross-node persistence acceptance

Extend the existing durable OAuth concurrency lane from distinct PostgreSQL
sessions in one VM to two independently supervised BEAM processes. Assert distinct
OS process IDs and PostgreSQL backend IDs between the peers. Their OS identities
also differ from the parent; its database backend ID is not part of the assertion.
Each peer uses a one-connection pool against the same committed test database;
public repository operations execute inside that peer. ExUnit owns peer lifetimes
and tenant cleanup runs after supervised workers and peers stop.

Keep database acceptance separate from Console's token HTTP and ExMCP transport
acceptance. This checkpoint does not close the complete cross-node milestone gate.
No production behavior changes; these are stronger checks of existing contracts.

The first fixture boot attempted the complete Persistence application and reached
an unrelated Call Engine configuration prerequisite. Use a small test application
that supervises only Repo and starts its real database/crypto dependencies instead.
A compiled support-module clock lets both peers deserialize the controlled time.
All peers finish booting before the bounded race barrier begins.

The five original races now run across peers: one-time attempt claim, prune versus
claim, tenant pending-attempt cap, exclusive refresh claim, and refresh completion
versus revocation. Two deterministic cases add revocation while another node holds
a claim and abrupt claimant VM termination. The surviving node cannot acquire the
claim before its deadline, cannot reclaim or complete it at the exact deadline,
and observes the unchanged encrypted grant with its original fence. The initial
grant revision is allowed to be implicit, so the final assertion compares the
entire unchanged grant rather than requiring a materialized revision field.
