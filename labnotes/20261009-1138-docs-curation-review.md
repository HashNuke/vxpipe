The requested deliverable is this labnote for human review. The three dispositions are:

1. **Labnote**: historical investigation, experiment, implementation narrative, review or evidence. Preserve chronology and limitations in a top-level `labnotes/YYYYMMDD-HHMM-two-to-four-word-task.md` file.
2. **Milestone**: delivery specifications, ordered packages, prerequisites and acceptance checklists. Consolidate into the existing descriptive, unnumbered `labnotes/milestones/` identity where possible.

Documentation review does not prove implementation or live-provider acceptance.

## Proposed documentation structure

Use `docs/index.md` as the entry point, with a small set of organized sections:

- `docs/getting-started/`: supported installation and first-call paths; explicit availability for pending distributions.
- `docs/guides/`: operator workflows, call-spec authoring, tenant setup and credentials.
- `docs/development/`: checkout setup, fixtures, live tests, browser/media checks and formal verification.
- `docs/reference/`: public schemas, API/protocol contracts, runtime ownership, providers and reusable client packages.

Canonical ownership: `docs/reference/provider-registry.md` owns provider manifests and model-list descriptor schemas; `docs/reference/model-catalog.md` owns authoring discovery/filtering and selection semantics. `docs/reference/readiness.md` owns resource evidence, Watch notifications and waiting behavior; runtime lifecycle pages link to it.

Maintain a concise architecture overview with links to specific contracts. Avoid copying the same contract into several guides. Public documentation should distinguish supported behavior from planned behavior and link to milestones for implementation work.
